## How work is done here

This project is spec-driven via [OpenSpec](https://openspec.dev/). The pipeline is fixed:

```
Docs/JIRA/DevMgmt/000N-<Epic>/FEAT-000N-0M-<Name>.md   <- a story, written by the PO
   -> /opsx:propose <change-id>     (the change id is named in the story)
   -> /opsx:apply
   -> /opsx:verify
   -> /opsx:archive
```

**One story, one OpenSpec change.** Do not batch a whole feature into a single change; the acceptance
criteria are written at story granularity so each `/opsx:apply` stays inside a reviewable diff.

Do not invent work that is not in the backlog. If something is needed and missing, add a story to the
appropriate feature file first — the backlog is the plan of record, and a change with no story behind it
has no acceptance criteria to verify against.

## The rules the architecture depends on

These are not style preferences. Violating any of them breaks a load-bearing property of the design.

1. **Agent services never open a database connection.** An agent's tool is an MCP or HTTP call. Exactly one
   process per domain reads `<DOMAIN>_STORE`. If a tool needs data the API does not expose, add an endpoint —
   never a connection string.

2. **An MCP server is a façade over HTTP endpoints, never over the database.** MCP sits inside the agent
   plane, not underneath it.

3. **Read tools and write tools live on separate MCP servers.** `issue_card` and `submit_order` are never on
   the same server as `search_menu`, so a read-only agent physically cannot call a write tool.

4. **Money and availability are never generated by a model.** Totals come from `price_order()`; balances come
   from the ledger tool; slot availability comes from `events-api`. An agent may not state a monetary amount
   that did not come back from a tool call in the current turn.

5. **Reference data is pluggable; transactional data is Postgres, always.** Menu items and event templates may
   live in JSON shards. Orders, bookings, holds and the gift card ledger may not.

6. **Nothing scans the shard corpus at request time.** 100k files per domain is a multi-minute read. Every
   query path goes through an index; only the indexer bulk-reads shards.

7. **Three agent frameworks means three dependency sets and three containers.** Never put ADK and LangChain
   in one virtualenv — `google-genai` pin conflicts. `Middleware/shared` stays dependency-light.

## Build order (do not reorder)

1. **Portals first (epics 0001–0004)** against contract stubs, including a mock agent service that speaks the
   real SSE envelope. The API shape is settled by looking at real screens.
2. **Domain services (0005–0012)** — identity and branch scope first, then catalog, orders, events,
   gift cards and the corpus.
3. **MCP layer (0013)**, then the agents (0014–0016) and observability (0017).
4. **Cloud workflows (0018)**.

The mock agent service in `FEAT-0003-02` exists so epic 0003 does not depend on epics 0014–0016. That is
deliberate; do not "simplify" it by waiting for the real agents.

## Configuration seams

Two switches, each per-service, each read in exactly one place.

- **LLM provider:** `<SERVICE>_LLM_PROVIDER` ∈ `gemini | bedrock | azure_openai | huggingface | ollama`.
  LangChain and LangGraph have native integrations for all of them; **ADK reaches non-Gemini providers
  through LiteLLM**, where tool-calling fidelity varies. No provider is "supported" until it passes the
  conformance suite in epic 0017.
- **Data store:** `<DOMAIN>_STORE` ∈ `postgres | json | hybrid`. Keep the parametrized contract suite green
  across every implementation — that suite is the only thing stopping the modes from diverging.

Embedding dimensions differ per provider (768 / 1024 / 1536 / 384). Key embedding tables on
`(provider, model, dim)`; never mix vector spaces in one index.

## Infrastructure

- **AWS: CloudFormation. Azure and GCP: Terraform.** One numbered block is one stack or one state.
- GitHub Actions are `workflow_dispatch` only, named `<CLOUD>-<NNNN>-<Setup|Destroy>-<Target>.yml`.
  **The number is the dependency order** — Setup ascending, Destroy descending.
- On AWS, cross-stack exports make CloudFormation refuse an out-of-order delete. On Azure and GCP the
  reusable Destroy workflow must implement that check itself.

## Local development

Once `DevOps/Local` exists (epic 0005): `./DevOps/Local/docker-all-up.sh` brings up the network, Postgres and
Redis, runs migrations, bootstraps the index, then starts APIs, MCP servers, agents, gateway and portals —
health-gated at each step. `docker-all-status.sh` prints each service's resolved provider and store, which is
the fastest way to answer "which model is this actually using".

## Working in this repo

- Ports are documented in `README.md`; use them rather than picking new ones.
- Prefer adding to an existing domain API over creating a new service. There are six services by design.
- Any user-facing change must be reachable in the running app via `docker-all-up.sh` with no manual steps
  beyond the documented `.env` — that is part of the Definition of Done in `Docs/JIRA/DevMgmt/README.md`.
