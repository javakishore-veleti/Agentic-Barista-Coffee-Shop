01 — ScopeWhat we are actually building

A customer-facing coffee shop platform for Brakeman's with three agentic capabilities, each a separate conversation with its own memory, its own tools, and its own failure modes:

  • Coffee ordering — browse and order from the live menu. Grounded in the real catalog: Brakeman's Blend (plum, brown sugar, molasses; Guatemala and Colombia), the Queen Bee iced honey cinnamon oat latte, LoCoMocha, Ticket to London, Slow-berry Matcha, Barb's Butter Bars in Oreo or Almond Joy, rotating Lenny Boy Kombucha, plus retail — 12 oz whole bean at $17.50, mugs $12–$30, long sleeve at $24.
  • Private events — a booking conversation with real constraints: weeknights and Sundays only, 2 hours at $300 on a weeknight (7–9pm), $400 for 2 hours or $500 for 3 hours on a Sunday, plus 1 hour setup and 30 minutes cleanup that must be reserved alongside the event window.
  • Gift cards — issue, reload, and check balance. $5 / $10 / $20 / $50 / custom, for one recipient or as a pooled group card, delivered by SMS or email, now or scheduled.

Three things are non-negotiable inputs to the design, and they drive most of what follows: the LLM provider is per-service configurable (Bedrock, Gemini, Azure OpenAI, Hugging Face); the data store is per-service configurable (Postgres, JSON shards, or a mix); and the reference corpus is roughly 300,000 JSON files — 100k of coffee, 100k of events, 100k of gift card configurations.

02 — StructureThe two planes, and the one rule between them

The single most important decision in this design is a boundary: agent services never open a database connection. They call domain APIs over HTTP, and those APIs own persistence entirely.

The rule

An agent's tool is an HTTP client, not a query. CATALOG_STORE is read by exactly one process — catalog-api — not by the barista agent, not by the admin portal, not by the indexer's caller.

Break this rule and you implement the Postgres-or-JSON switch four times and it drifts three ways. Keep it and the admin portal, the agent, and any future integration all see identical menu data by construction, because they are hitting the same endpoint.

The three agent services get three separate dependency sets and three containers. 04 — AgentsThree domains, three frameworks, three reasons

The frameworks are not interchangeable decoration here — each domain has a different control-flow shape, and each framework is genuinely the better fit for its shape.

Google ADK

Barista

A tool-calling loop over a large catalog. Open-ended questions, cheap retrieval, no required order of operations — exactly what a plain LlmAgent with tools does well.

  • search_menu(query, filters)
  • get_item(item_id)
  • start_order() / add_item()
  • price_order() — deterministic
  • submit_order()

Why ADK: the domain needs breadth of retrieval, not workflow. ADK's session service and tool loop cover it with the least machinery.

LangGraph

Private events

A stateful booking workflow with validation gates and a human in the middle. Nodes: collect → check availability → quote → confirm → interrupt for staff approval → hold → submit.

  • find_slots(date, duration)
  • quote(day_type, hours)
  • hold_slot(slot_id, ttl)
  • submit_inquiry(...)
  • resume_after_approval()

Why LangGraph: the interrupt is the point. A half-finished booking must survive a page refresh and a staff decision, which is a checkpointed graph, not a chat loop.

LangChain

Gift cards

The smallest surface: a bounded tool-calling chain over a handful of configuration reads and three writes. No graph needed, no long-lived state.

  • list_denominations()
  • quote_card(amount, delivery)
  • issue_card(...)
  • reload_card(card_id, amount)
  • check_balance(card_id)

Why LangChain: it is the least framework that does the job, and it makes the contrast with the other two legible in the same repo.

Grounding rules that live in code, not in the prompt

Money is never generated. The gift card agent may not state a balance or a total that did not come back from a tool call in the current turn. Same for the barista: sizes, modifiers, and totals come from price_order(), so a latte with oat milk costs the same whether the model was feeling generous or not.

Availability is never inferred. A 2-hour Sunday event starting at 7pm occupies the room from 6:00pm to 9:30pm once setup and cleanup are counted. That arithmetic belongs in events-api, which is the only thing that knows the shop is closed Sundays and therefore rentable.

05 — ToolsThe MCP layer: one definition, three frameworks

Left alone, the design above has a duplication bug hiding in it. search_menu would be written three times — once as an ADK function tool, once as a LangChain @tool, and again for LangGraph — with three schemas, three sets of tests, and three opportunities to drift apart the first time the catalog gains a field.

Each domain therefore publishes one MCP server, and every agent framework consumes it.

MCP serverToolsConsumed by
catalog-mcpsearch_menu · get_item · price_orderbarista-agent, admin console, Claude Code
events-mcpfind_slots · quote · hold_slot · submit_inquiryevents-agent
giftcards-mcplist_denominations · quote_card · issue_card · reload_card · check_balancegiftcards-agent
ops-mcpindex_status · reindex_shards · shard_stats · resolve_interruptthe team, from Claude Code
MCP as a boundary, not just a format

Read tools and write tools live on separate servers. issue_card and submit_order are not on the same server as search_menu. An agent that only needs to read is handed only the read server, so it physically cannot call a write tool — a constraint no prompt injection can talk it out of, because the capability was never attached.

The two-plane rule from §02 still holds without exception: an MCP server is a façade over the domain API's HTTP endpoints, never over the database. MCP sits inside the agent plane, not underneath it. If a tool needs data the API does not expose, the fix is an endpoint, not a connection string.

Transport is stdio in local development — which is also what lets the team point Claude Code or Claude Desktop at ops-mcp and ask about index health in plain English — and streamable HTTP once deployed, behind the same OIDC the gateway uses.

Where MCP is not the answer

MCP costs a process and a hop. For a tool used by exactly one agent and nothing else, a plain in-process function is simpler and honest. The three domain servers earn their keep because each is consumed by an agent and by something outside it; a hypothetical fourth server used only by the barista would not.

06 — Seam onePer-service LLM provider

Middleware/shared/llm exposes two functions and nothing else: get_chat_model(service) and get_embedder(service). Each service names its own provider, so you can run Bedrock for the barista and Gemini for events in the same docker compose up. 

# Middleware/barista-agent/.env
BARISTA_LLM_PROVIDER=ollama          # the $0 default — see §15
BARISTA_LLM_MODEL=qwen2.5:7b
BARISTA_LLM_BASE_URL=http://ollama:11434
BARISTA_EMBED_PROVIDER=bedrock
BARISTA_EMBED_MODEL=amazon.titan-embed-text-v2:0   # 1024 dims

# Middleware/events-agent/.env
EVENTS_LLM_PROVIDER=gemini
EVENTS_LLM_MODEL=gemini-2.5-flash

# Middleware/giftcards-agent/.env
GIFTCARDS_LLM_PROVIDER=azure_openai
GIFTCARDS_LLM_MODEL=gpt-4o-mini

# the embedding provider is a SEPARATE switch from the chat provider
CATALOG_EMBED_PROVIDER=ollama
CATALOG_EMBED_MODEL=nomic-embed-text        # 768 dims, self-hosted
CATALOG_EMBED_BASE_URL=http://ollama:11434
Chat provider and embedding provider are not the same decision

They are configured independently on purpose. The chat provider can follow the cloud you deployed to; the embedding provider should not, because changing it invalidates every vector you own. Self-hosting the embedder — Ollama locally or in your own cloud — makes the vector space a constant you control, so an AWS deployment and a GCP deployment can differ on chat while sharing one index.

ProviderLangChain / LangGraphGoogle ADKEmbedding dims
geminiChatGoogleGenerativeAI — nativeNative Gemini768
bedrockChatBedrockConverse — nativevia LiteLlm wrapper1024 (Titan v2)

Two sharp edges

ADK off Gemini goes through LiteLLM. That path works, but tool-calling fidelity — parallel calls, strict JSON schemas, forced tool choice — differs by provider. Before committing the barista to Bedrock, run a fixed tool-calling conformance suite against every provider you intend to support and record the results; treat any provider that fails it as unsupported rather than discovering it in a demo.

Embedding dimensions are not portable. 768 / 1024 / 1536 / 384 are different vector spaces and different pgvector columns. Key the embedding table on (provider, model, dim) and never mix spaces in one index. Switching the catalog's embedding provider means re-embedding the whole corpus — a batch job with a progress table, not a Friday config change. Pinning the embedder to a self-hosted Ollama model is the cheapest way to make that day never arrive.

07 — Seam twoPer-service data store

Each domain API defines a Repository protocol and three implementations. The API code never branches on the store; it receives a repository at startup and calls it. 

# Middleware/catalog-api/.env
CATALOG_STORE=hybrid          # postgres | json | hybrid
CATALOG_JSON_ROOT=/data/coffee
CATALOG_PG_DSN=postgresql://brakemans@postgres:5432/catalog

# Middleware/events-api/.env
EVENTS_STORE=json            # event definitions from files…
EVENTS_BOOKING_PG_DSN=postgresql://brakemans@postgres:5432/events
                              // …bookings always Postgres. See rule below.
ModeReadsWritesSearchUse it for
json Shard file + in-process LRU Read-mostly; append journal SQLite FTS5 sidecar index Demos, air-gapped runs, showing the file-backed path works
postgres Indexed rows Transactional pgvector + trigram The default for anything real
hybrid Postgres (hot) Files authoritative, reconciled by indexer pgvector Document-lake pattern: files are truth, Postgres is the query engine
The constraint that makes this buildable

Reference data is pluggable. Transactional data is Postgres, always. Menu items, event templates, and gift card denominations can live in files. Orders, bookings, holds, and the gift card ledger cannot — they need atomicity, uniqueness, and an audit trail that a directory of JSON files will not give you at any level of effort.

So EVENTS_STORE=json means event definitions come from files while bookings still hit Postgres. Say this out loud in the config comments, or someone will set GIFTCARDS_STORE=json and quietly build a money ledger with no transactions.

Keeping the seam honest costs one test file per domain: a single contract suite, parametrized over every repository implementation, asserting identical results. If JsonShardRepository and PostgresRepository disagree, the suite fails — which is the only thing that stops "or a mix" from rotting into two incompatible behaviours.

08 — Seam threeIdentity: one token shape, four issuers

A service, authz-api, owns users, roles and branch scope. It is the only thing that knows which identity provider is in play, and it is configured exactly like the other two seams. 

AUTH_PROVIDER=basic          # basic | cognito | entra_id | gcp_identity
AUTH_PG_DSN=postgresql://brakemans@postgres:5432/authz
AUTH_TOKEN_TTL=3600
AUTH_ISSUER=https://auth.brakemans.local

The rule that makes the seam work

Whatever the provider, authz-api emits one internal principal shape. Nothing downstream ever sees a Cognito claim, an Entra claim or a password row — it sees this, and only this: 

principal = {
  sub, email,
  realm:        staff | customer,
  roles:        [ hq | regional | branch_manager | staff ] | [ customer | guest ],
  branch_scope: [ "*" ]  |  [ "br-0042", "br-0117", … ],
  iss, exp
}

Swapping basic for cognito is a deployment decision, not a code change — exactly as swapping Bedrock for Gemini is. The gateway verifies once and forwards a signed internal context header; domain services never call the identity provider.

Two realms, one service

Staff and customers authenticate against separate API surfaces inside the same service — /v1/staff/* and /v1/customer/* — with distinct user tables, token audiences and provider configuration, while sharing one principal shape, one verification path and one deployment. 

AUTH_STAFF_PROVIDER=cognito        # staff via the corporate pool
AUTH_CUSTOMER_PROVIDER=basic        # customers in our own Postgres

The realms are separate because their risk is not comparable — a compromised branch manager can reprice a region; a compromised customer can see their own order history — and because the two populations differ by orders of magnitude. Sharing a service keeps one token format and one set of verification middleware; sharing a user table would not.

Customer accounts, and the guest who does not want one

An account unlocks saved favourites, order history and a gift card wallet — which is what makes a global ledger (§09) useful to the person holding the card. It binds the cart and all three chat sessions to a durable identity, so a conversation survives a device change.

Guest ordering stays first-class. Nobody should create an account to buy a coffee. A guest gets an anonymous principal, a cart and a session; if they register later, the open cart, the three sessions and any in-flight order migrate to the new account. Design that migration now — retrofitting it means asking customers to lose their cart at signup.

Roles are the branch model, enforced

branch_scope is not a UI convenience — it is checked in the domain APIs, the only things that can enforce it. A branch manager sets availability and daily rotation for branches in their scope and nothing else; regional sets event rate cards; menu edits are HQ-only, because the menu is brand-wide. A request whose principal lacks scope for the branch it names is rejected at the API, whether it came from a portal, an agent, or a script.

Agents run as the customer

An agent holds no service account. It carries the caller's principal through to every MCP tool call, which is what makes the read/write server split from §05 real: the write server requires a principal with matching scope, so an agent given only the read server and a customer principal is doubly unable to issue a gift card. Capability and authority are separate checks; both must pass.

Local auth is real auth

AUTH_PROVIDER=basic locally means a seeded user table, argon2id hashing, and genuine token issuance and verification — not a header-injected fake user. If local identity is fake, every authorization bug you have ships, because nothing in the development loop ever exercised the check. Seed one user per role so scope violations surface on a laptop.

09 — DomainOne menu, a thousand branches, a thousand calendars

Brakeman's runs 1,000 branches across the United States, and the three domains do not scale the same way across them. This distinction decides whether the corpus is a modest indexing job or an eye-watering one.

DomainVaries by branch?What actually differs
MenuNo — brand-wide and identicalOnly availability, the daily rotation (today's pastry, today's kombucha), and occasional regional price adjustment
EventsYes — substantiallyBranch size tier sets capacity, which event types it can host, and what it can afford to staff — and therefore its rate card and durations
Gift cardsNo — and must notA card bought in Matthews has to redeem in Charlotte. Branch is an attribute of a transaction, never a partition of the balance

What this does to the catalog

catalog_items        ~50 rows    brand-wide, canonical, embedded exactly once
branch_profile       1,000 rows  tier, seats, rentable?, region, tax jurisdiction, timezone
branch_availability  (branch_id, item_id, effective_date)
                                 → available, price_override, rotation_selection
event_capability     (branch_id) → tier → capacity, hostable types, rate card
The rule that falls out of it

Semantic search runs once, brand-wide. Availability filtering runs per branch, relationally. search_menu(query, branch_id) searches the ~50 canonical items by vector, then filters the result against that branch's availability for today. Never embed per branch — the vectors would be a thousand identical copies of the same fifty.

What this does to the corpus

  • 100k coffee shards = 1,000 branches × ~100 dated menu snapshots. Item definitions are byte-identical across every one. Dedupe by content hash and the distinct set to embed is about fifty items, not ten million.
  • What genuinely needs indexing at scale is availability, not text: 1,000 branches × ~50 items × 365 days is on the order of 18 million rows a year. That is a b-tree on (branch_id, effective_date) — a relational problem. Do not reach for pgvector to solve it.
  • The 100k event shards are the corpus that earns the shard machinery. Branch calendars genuinely differ — dates, capacities, rate cards — so dedupe buys little and the indexer does real work.
  • The 100k gift card shards are brand-wide configuration × branch participation — which denominations a branch promotes, which branch-funded promos run where. The ledger stays in Postgres regardless of what the shards say.

Tiering is data, not an enum

How many tiers there are, and what puts a branch in one, must be queryable and changeable without a deploy — because the tier definition is the events pricing model for 999 branches. 

branch_metrics     branch_id · seats · sqft · staff_headcount · has_private_area
                   measured_at                          # observed facts
branch_tier        tier_id · name · min_seats · max_seats · min_sqft
                   max_event_guests · staffing_cost_index · sort_order
tier_event_type    tier_id · event_type                   # what a tier may host
event_rate_card    tier_id · day_type (weeknight|sunday) · duration_hours
                   price · setup_minutes · cleanup_minutes · effective_from
branch_profile     … · tier_id · tier_assigned_at · tier_assigned_by (auto|manual)
How a branch gets its tier

Seats is the primary driver, because event capacity is literally seats; square footage breaks ties; staffing_cost_index modifies price, never capacity. A nightly job evaluates branch_metrics against branch_tier bands and writes the assignment.

Manual pinning is supported and recorded. A branch with an awkward layout can be pinned to a lower tier with a reason; tier_assigned_by = manual means the nightly job leaves it alone. Without this the first exception becomes a hardcoded branch id in a query.

Start with four tiers and let the table prove or disprove that number. Matthews seeds the mid tier: weeknight 2h $300, Sunday 2h $400 and 3h $500, 60 minutes setup, 30 minutes cleanup — real rows in event_rate_card, not constants in code.

Price authority is a policy table with an approval trail

The menu is brand-wide, yet price_override exists per branch. Who may set one, and by how much, is data — so the first exception is a row, not an ad-hoc database edit at 11pm. 

price_policy             scope (brand|region|branch) · category · role_required
                          max_delta_pct · max_delta_abs · requires_approval_above_pct
price_override_request   branch_id · item_id · proposed_price · reason
                          requested_by · requested_at · status
                          approved_by · approved_at · effective_from · effective_to

                          effective_from · effective_to      # the applied result
The workflow the tables encode

A regional manager proposes an override. If it falls inside their policy band it is applied immediately; if it exceeds requires_approval_above_pct it escalates to HQ and sits as pending. Either way there is a request row with a reason, an actor and a timestamp — so "why is a latte $6.25 in Raleigh" has an answer.

Overrides are effective-dated, and orders snapshot the price anyway (§10). The two mechanisms are complementary: the override table explains what the price is, the order line records what it was when someone paid it.

Branch context is not optional

Every conversation carries a branch_id, and it is a required parameter on nearly every MCP tool. A tool called without one fails loudly rather than defaulting to a flagship branch — a barista that quietly answers from Matthews' availability while the customer is standing in Raleigh is worse than one that asks which store.

The reference branch in the fixtures is modelled on a real independent shop in Matthews, NC, whose published figures seed the mid tier — 2 hours at $300 on a weeknight, $400 for 2 hours or $500 for 3 on a Sunday, 1 hour setup and 30 minutes cleanup — seed the mid-size tier the other 999 derive from.

10 — DomainThe order is a commerce document, not a list of drinks

A submitted order is a standard order-management structure: a header, lines, line modifiers, and many discounts and taxes, plus shipping where the goods actually ship. Modelling it as "a cart with a total" works right up until the first promotion, and then never again. 

order_header          order_id · branch_id · customer_ref · channel (web|chat|pos)
                      status · currency · placed_at · fulfil_at
                      subtotal · discount_total · tax_total · shipping_total · grand_total
order_line            line_no · item_id · item_snapshot · qty · unit_price
                      line_subtotal · line_discount_total · line_tax_total · line_total
order_line_modifier   modifier_id · snapshot · price_delta
order_discount        code · scope (order|line) · type (pct|amount) · value
                      sequence · applied_amount
order_tax             scope (order|line) · jurisdiction · rate · taxable_base · tax_amount
order_shipping        method · address_ref · cost · tax_amount        # retail only
order_payment         method (giftcard|card|mock) · amount · ref · status
order_event           append-only status transitions, with actor
Four rules this structure exists to enforce

1. Lines snapshot the item. A line stores the name, description and price as of purchase. The menu is brand-wide and mutable; an order must not silently change when HQ edits a price two months later.

2. Discounts are ordered and their result is stored. Ten percent off then two dollars off is not the same as two dollars off then ten percent. sequence is part of the data, and applied_amount is written down rather than recomputed at read time.

3. Taxes are many, and per jurisdiction. A thousand branches across the United States means state, county and prepared-food rates that differ by branch and by item category — which is why branch_profile carries a tax jurisdiction. Taxes attach per line, not per order.

4. Totals are stored, never derived on read. Recomputing a two-year-old order under today's rates produces a confidently wrong number, and it will be wrong in an audit.

Where tax rates come from

A versioned rate table — Postgres or a JSON file, per the same store seam as everything else — loaded into an in-process cache when a pod starts. No external tax service, no network hop on the ordering path.

                   rate · effective_from · effective_to · rate_version

Three rules the cache has to obey

Rates are effective-dated and orders record the version used. order_tax stores the resolved rate and its rate_version, so a two-year-old order can be explained without guessing which table priced it.

A pod that cannot load rates fails readiness. It does not start serving with an empty cache and quietly compute zero tax. That is a silent financial defect, and the only safe failure mode is not taking traffic.

Invalidation is explicit, not TTL-guessed. Pods poll the single cheap rate_version value and reload the set when it changes, so every pod in the cluster converges within a poll interval — no restart, no redeploy.

Shipping applies to retail only. Whole bean at $17.50, mugs and shirts can ship; drinks and pastries are pickup at a branch. The model carries shipping on every order and a drinks-only order simply has none — rather than two order types that diverge.

Fulfilment: mocked, contract-shaped — the same call as payments

A submitted order does not stop at a persisted record; it reaches a PosAdapter whose methods mirror a real point-of-sale — submit ticket, poll status, void, close. MockPosAdapter moves a ticket through accepted → in progress → ready → collected on a timer and writes each transition to order_event.

Consistent with the payment decision: real contract, no real integration. The agent and the portal both watch order_event, so the day a real POS is wired in, neither changes.

And the rule from §04 applies with full force here: the model never computes any of this. price_order() returns the complete priced document — every discount line, every tax line, every total — and the agent's only job is to read it out.

11 — Scale300,000 files, and why file-backed still needs an index

300,000 shard files across the three domains, structured as described in §09 — 1,000 branches × roughly 100 dated snapshots each. Three consequences fall straight out of those numbers, and they hold whichever store mode is configured.

  • Nothing may scan the corpus at request time. Opening 100,000 files to answer "do you have anything with oat milk" is a multi-minute operation. Every query path goes through an index; the shards are bulk-read exactly once, by the indexer.
  • File-backed does not mean index-free. In json mode the index is a SQLite sidecar (FTS5 for lexical, a flat vector table for semantic) written next to the corpus. You lose Postgres, not indexing.
  • Item ids encode location. cof:00042:017 is shard 42, offset 17 — an O(1) fetch that opens one 30 KB file and indexes into a list, with the parsed shard cached in an LRU and hot items in Redis.

The indexer is incremental and idempotent. A shards table holds (shard_id, path, sha256, item_count, mtime, indexed_at); a run diffs checksums, re-reads only what changed, and is safe to kill and restart. It is a job, not a service — triggered on deploy, by the admin portal, or by a file watcher in local dev.

Do the arithmetic before you embed

Embedding every shard row naively is roughly 40 GB of raw vectors at 1024 dimensions before index overhead, plus an embedding bill to match. Embedding the deduplicated canonical catalog — the ~50 distinct items from §09 — is a few hundred kilobytes and costs cents. Nothing about the corpus changed between those two numbers; the only difference is whether you hash content and embed the distinct set before you start. Treat any pipeline that embeds per-shard rather than per-distinct-item as a defect, not a tuning opportunity.

12 — ContractOne chat envelope, three windows

The windows are independent, but they share a wire format — which is what lets Angular have one <chat-panel> component instead of three, and leaves the door open to a routing supervisor later without redesigning the front end. 

POST /v1/chat/{surface}/{session_id}   →  text/event-stream
     surface ∈ { barista, events, giftcards }

→  { "message": "something iced and not too sweet", "context": {...} }

←  event: token        { "text": "The Queen Bee is" }
    event: tool_call    { "name": "search_menu", "args": {...} }

    event: ui_action   { "kind": "order_summary", "payload": {...} }
    event: error        { "code": "provider_timeout", "retryable": true }

ui_action is the piece worth designing carefully. It is how an agent pushes a real Angular component into the transcript — a priced order summary, an event quote with the setup window drawn in, a gift card preview with the recipient and delivery time — instead of asking the model to draw a table in text. Structured payload in, typed component out; the model never formats money.

Sessions are namespaced per surface (sess:barista:{id}) in Redis, so the three windows genuinely do not share memory. The events agent additionally checkpoints its graph to Postgres, because its state has to outlive the browser tab.

The number is not decoration: it is the dependency order. Each Destroy guards on "no higher-numbered stack still exists" and refuses rather than orphaning resources.

Mechanically: each numbered file is a thin dispatch wrapper over a reusable workflow in .github/workflows/_reusable/, so the deploy steps exist once rather than sixty times. Auth is OIDC federation to each cloud — no long-lived keys in secrets. Every workflow takes an environment input, and every Destroy takes a typed confirmation input that must match the environment name before the job proceeds. A concurrency group keyed on (cloud, env, block) prevents a Setup and a Destroy from racing on the same stack.

Two toolchains, on purpose

AWS uses CloudFormation. Azure and GCP use Terraform. One numbered block is one CloudFormation stack on AWS and one Terraform state on the others, so 0100-Destroy-Postgres is a single delete-stack or a single scoped destroy — never a hunt through a console for orphaned resources.

What CloudFormation gives you for free

Because each stack publishes its outputs as exports and the next block up imports them, CloudFormation refuses to delete a stack whose exports are still in use. The reverse-order teardown rule stops being a convention the workflow has to police and becomes an API-level guarantee — 0001-Destroy-Network simply fails while anything above it is alive.

Terraform gives you no such guard across separate states, so the Azure and GCP Destroy workflows must implement the check themselves: query for a higher-numbered stack's state before destroying, and refuse. Write that check once in the reusable workflow, not once per block.

The cost of the split is a shared stack interface that has to be honoured twice — same block numbers, same inputs, same outputs, expressed in two dialects. Keep that contract in DevOps/Cloud/contracts/ as plain documented parameter and output names, and review any change to it against all three clouds at once.

The payoff of seam one

Because the provider abstraction already exists, the same container images run on all three clouds — AWS deploys set *_LLM_PROVIDER=bedrock, Azure sets azure_openai, GCP sets gemini. The templates differ — CloudFormation on one side, Terraform on the other. The application does not.

Target: $0 standing cost, and no more than $1 for a full cloud provision–demo–destroy cycle. Every default below follows from that. None of them weaken the seams — the seams are precisely what make a free default safe, because the day the budget changes, the provider is a variable rather than a project.

This is exactly why AWS got CloudFormation

Under this posture the numbered Destroy workflows are routine, not emergency equipment — the AWS stack goes up for a demonstration and comes down the same afternoon. Export-enforced teardown ordering (§14) stops being a nicety and becomes the thing that makes a same-day destroy safe enough to run without reading the console first.

The Kubernetes note, since the tax cache assumed pods

The rate-cache design in §10 is unchanged by dropping Kubernetes: it caches per instance rather than per pod, still fails readiness when rates will not load, and still converges on a rate_version poll. Cloud Run and Container Apps both honour a readiness signal. If you want to exercise manifests anyway, run kind or k3d locally — also $0.

What the dollar actually costs you

A 7B model on a laptop is slower than a frontier model and materially weaker at tool calling — which is the one capability this entire architecture rests on. Do not treat "a small local model reliably calls our tools with the right arguments" as an assumption. It is the first experiment, it belongs in the conformance suite before any agent work starts, and if it fails the answer is Gemini's free tier for the barista rather than redesigning the tools.

The second cost is honesty about the demo: a sampled cloud corpus proves the pipeline, not the scale. Claims about 300k-shard performance stay backed by local runs.

16 — PortalsCustomer and admin

Portals/CoffeeShop — the menu, hours, location, and three chat surfaces reached as three routes or a segmented control. One <chat-panel> component parametrized by surface, streaming over EventSource, rendering ui_action payloads as typed Angular components. Signals for transcript state; no shared store between surfaces, matching the backend isolation.

Portals/CoffeeShopAdmin — catalog CRUD with shard and index health, the event inquiry queue, the gift card ledger and denomination config, and an agent console showing live sessions, tool call traces, token spend by provider, and prompt versions.

The join worth building

Staff approving an event inquiry in the admin portal resolves the LangGraph interrupt for that booking — the customer's chat, still open or reopened days later from the checkpoint, picks up exactly where it paused and confirms. That single path is the clearest demonstration of why events got a graph and the other two did not, so build it early rather than as a stretch goal.

17 — SequenceBuild order

Each step is runnable and demonstrable before the next begins. Numbering is dependency order, not preference.

01

Skeleton and shared package

Middleware/shared with config, telemetry, and the two seams as protocols with one implementation each. DevOps/Local scripts bringing up Postgres and Redis. Nothing agentic yet.

02

Corpus generator and indexer

Seed/generate_shards.py produces the real 300k-file corpus from the actual Brakeman's menu with realistic variation. The indexer walks it. Now you have honest numbers for dedupe ratio, index size, and embedding cost before committing to a provider.

03

catalog-api, all three store modes

The first domain API end to end, with the parametrized contract suite proving json, postgres, and hybrid agree. This step validates the seam design; if it is awkward here, fix it before two more APIs inherit the shape.

04

barista-agent + one chat surface

ADK on Gemini first (the native path), gateway, SSE, and the Angular chat panel. First vertical slice — a customer can order coffee. Add the LiteLLM providers only once the Gemini path is solid.

05

Provider conformance suite

The tool-calling matrix across Bedrock, Azure, and Hugging Face for both framework families. Publish the results table into the repo. This is what turns "configurable" from an aspiration into a supported list.

06

events-api + events-agent + admin approval

The LangGraph graph, the Postgres checkpointer, and the interrupt resolved from the admin portal. The hardest and most interesting slice.

07

giftcards-api + agent, mocked adapters

PaymentGateway and GiftCardIssuer protocols shaped like Square's Gift Cards and Payments APIs, with a Postgres-backed mock ledger behind them. No real money, real contract.

08

Cloud workflows, one cloud at a time

AWS blocks 0001→0900 first, proven by a full Setup-All and Destroy-All cycle in a scratch account. Only then clone the numbering to Azure and GCP.

18 — OpenCalls still to make

Risk

Two IaC dialects will drift. CloudFormation on AWS and Terraform on Azure and GCP is a deliberate trade — clean delete-stack teardown and export-enforced ordering in exchange for writing every block twice. The mitigation is the shared stack contract and a rule that no block is considered done until both dialects implement it; the failure mode is AWS racing ahead and the other two quietly becoming stale.

Risk

Rate and tier maintenance. The rate table and the tier bands are the right mechanisms, but somebody has to keep them current — US tax rates change quarterly, and a branch that adds seats changes tier and therefore its event pricing. Own both as scheduled jobs that emit a diff report; the failure mode is silent, correct-looking, and found by an auditor.

Decide

Initial tier bands. Four tiers is the starting assumption and the table can prove it wrong, but the seat thresholds themselves still need a first pass from someone who knows the estate. Matthews anchors the middle; the boundaries are a product call, not a schema one.

Risk

Cross-branch gift card liability. A global ledger is the right call and the only one matching customer expectation, but any branch can redeem value another branch sold. Inter-branch reconciliation is a finance concern the mocked adapters will never surface — flag it before the mock is swapped for real issuance.

Decide
Risk

ADK + LiteLLM + a small local model. This is the single likeliest thing to force a redesign, and the $0 posture puts it on the critical path rather than the margin: ADK reaches Ollama through LiteLLM, and a 7B model's tool-calling fidelity is the weakest link in the chain. Run that conformance experiment first, before any agent code. If it fails, the fallback is Gemini's free tier for the barista only — the abstraction and the other two agents are unaffected.

Risk

Re-embedding cost. Changing the catalog's embedding provider invalidates every vector. Treat the embedding provider as an environment-level constant, not a per-request knob, and budget a migration job for the day it changes.

Scope

Guest-to-account migration. Customer accounts are in from the start, and so is guest ordering — so the cart, all three chat sessions, any in-flight order and a just-purchased gift card have to survive a guest registering mid-flow. Easy to design now, genuinely painful to retrofit; specify it before the first customer-facing slice ships.
